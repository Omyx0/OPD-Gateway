# ANTIGRAVITY FULL BUILD PLAN
## Smart Digital OPD Management System with AI-Based Patient Triage

**Document:** 13 / 14  
**Purpose:** Master implementation guide for building the complete semester web application in Google Antigravity  
**Frontend:** React + Vite + Tailwind + shadcn/ui  
**Frontend first-pass:** Lovable — frontend only  
**Main implementation:** Google Antigravity  
**Backend:** Node.js + Express  
**Database:** Supabase PostgreSQL + PostGIS  
**Authentication:** Supabase Auth  
**Security:** JWT + RBAC + RLS  
**Realtime:** Socket.io  
**AI:** Gemini API  
**ML:** Python + FastAPI + scikit-learn  
**Status:** Full build execution plan

---

# 3. WHY LOVABLE IS FRONTEND-ONLY

Lovable may automatically attempt to create:

```text
Auth
Database
Supabase integration
Backend logic
```

That would conflict with the final architecture.

Therefore:

```text
Lovable
→ visual prototype

Antigravity
→ actual system implementation
```

Any backend-like code generated by Lovable should be removed, isolated or replaced during Antigravity integration.

# 70. ANTIGRAVITY WORKING METHOD

Antigravity should work incrementally.

For each phase:

```text
1. Inspect current code
2. Identify dependencies
3. Implement one module
4. Run tests
5. Fix errors
6. Verify integration
7. Commit
8. Move to next phase
```

Do not ask Antigravity to rewrite the entire project in one operation.

---

# 71. ANTIGRAVITY MASTER INSTRUCTION

Give Antigravity this principle:

```text
Do not change the approved architecture without explicit approval.

Do not replace Supabase PostgreSQL with another database.

Do not add Firebase.

Do not create a duplicate authentication system.

Do not expose API keys.

Do not let the frontend become the source of truth.

Do not remove JWT, RBAC, RLS or Socket.io.

Do not replace the custom ML pipeline with an AI API-only solution.

Preserve existing working UI unless a change is required.

Implement incrementally and test after each phase.
```
